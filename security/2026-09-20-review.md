# Handover CMS security review

Reviewed **20 September 2026**, against Handover commit **768200e828e3d958e7f665c0f967e30a9e2a2672**.

## Remediation status

The accompanying security commit implements SEC-01, SEC-02, SEC-04, SEC-05 and SEC-06,
and the code and installer changes for SEC-03. Dependency audits of the CMS, demo and
scratch working trees report zero known advisories after the updates. The report below
preserves the original findings and their reviewed source locations.

SEC-03 still requires deployment configuration: create/bind a private `MEDIA_UPLOADS`
bucket, keep all public access off, add a one-day `uploads/` lifecycle rule, apply the
schema-version-11 migration, remove or expire old public staging objects, and set
`X-Content-Type-Options: nosniff` on the public media hostname. See the
[rollout instructions](../docs/media.md). Live Cloudflare configuration could not be verified
with the available local credentials; code completion does not confirm those controls.

## High-priority dependency maintenance

### SEC-01 — Update the actual locked dependencies, including bundled browser code

**Where**

- [CMS lockfile: Astro 7.2.4](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/pnpm-lock.yaml#L2081) and [Sharp versions](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/pnpm-lock.yaml#L3359).
- [Demo lockfile](https://github.com/MartinConde/handover-demo/blob/11ccfe3/pnpm-lock.yaml#L1640), [scratch lockfile](https://github.com/MartinConde/handover-scratch/blob/c700204bb1843d4e12fb091fda5cfbea32eb0af1/pnpm-lock.yaml#L1463).
- [Bundled editor dependencies](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/ui/package.json#L29).
- [Demo packaging and deployment scripts](https://github.com/MartinConde/handover-demo/blob/11ccfe3/package.json#L12).

**What / why**

The locks contain Astro **7.2.4** and Sharp **0.35.2 / 0.35.3**. Astro's advisory identifies possible code execution when its Sharp service processes a malicious AVIF; Astro **7.2.8** requires the fixed Sharp **0.35.4**. If this path is enabled, processing an attacker-controlled image can compromise the process doing the optimization, including a build process. Sources: [Astro advisory](https://github.com/withastro/astro/security/advisories/GHSA-26w7-cxv4-gfx2), [Sharp advisory](https://github.com/lovell/sharp/security/advisories/GHSA-rgj7-g3m4-5g8c).

Handover accepts AVIF uploads, but acceptance alone does not establish this exploit: I found no explicit Astro Image/Picture/getImage use in the demo or scratch source. Cloudflare's image pipeline also needs to be considered separately from Node-based Sharp processing. Patch promptly without treating the advisory as evidence that the deployed site has been compromised.

There are additional dependency updates worth doing in the same maintenance pass:

| Package | Found | Patched version reported by registry | Relevance |
|---|---|---|---|
| Astro | 7.2.4 | 7.2.8+ | AVIF issue above |
| Sharp | 0.35.2, 0.35.3 | 0.35.4+ | Astro and local Miniflare dependency paths |
| Tiptap core | 3.30.2 | 3.30.5+ | Covers attribute-merging and Markdown parser fixes; ship the matching Tiptap packages together |
| Vitest / @vitest/mocker | 3.2.7 | 4.1.11+ | Development-server file-read advisory |
| esbuild, nested under Drizzle tooling | 0.18.20 | 0.25.0+ | Development-server cross-origin disclosure |
| undici | 7.28.0 | 7.29.0+ | Multiple interceptor/cache/cookie advisories; affected features not established as CMS-reachable |
| js-yaml | 4.3.1 | 4.3.2+ | Merge-processing CPU exhaustion in tooling dependencies; Handover's content parser uses the separate yaml package |
| SVGO | 4.0.2 | 4.1.0+ | SVG sanitization advisories; no CMS SVG-upload path found |
| fast-uri, demo dependency tree | 3.1.5 | 3.1.6+ | Registry flags four high-severity advisories; production input path not demonstrated |

The Tiptap library is included in the shipped admin JavaScript despite being declared under devDependencies. A production-only dependency audit therefore misses relevant client code. Conversely, the production-only audit includes some development tooling through peer resolution; its results are not all production vulnerabilities.

The current editor uses fixed extensions. I did not find an application call to the vulnerable Tiptap attribute/shortcode helpers or demonstrate Tiptap XSS/CPU exhaustion in Handover. Likewise, the Vitest advisory requires particular exposed mocker/browser-server configurations; a normal test run is not proof of that exposure. Sources: [Tiptap parser advisory](https://github.com/ueberdosis/tiptap/security/advisories/GHSA-j95f-988m-3j2f), [Tiptap attribute advisory](https://github.com/ueberdosis/tiptap/security/advisories/GHSA-cp6q-959q-f8rh), [Vitest advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9).

**Suggested fix**

Refresh the affected direct dependencies and their lockfile resolutions in each project. Resolve transitive copies through compatible parent updates, checking major-version overrides carefully. Rebuild the admin UI and repack the demo's vendor tarballs; otherwise its deployment can retain the old bundled editor after the main workspace is fixed. Keep Better Auth's existing schema/runtime compatibility constraint in mind when updating its dependency tree.

**Done when**

The locks and installed trees resolve the fixed versions, the UI/fixture/package and deployment builds pass, and the corresponding advisories disappear on a repeat full audit. The full version/path/advisory inventory is in [security_dependency_audit.json](/Users/manc/Projects/handover-cms/security_dependency_audit.json).

## Medium-priority findings

### SEC-02 — Redirect sources bypass protection for existing pages

**Where**

- [redirectSourceError](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/core/src/lifecycle.ts#L42) accepts any slash-prefixed source without whitespace.
- [redirectError](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/core/src/lifecycle.ts#L274) compares raw strings against the served-page map and other rules.
- [redirectsText](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/core/src/lifecycle.ts#L523) then emits both slash forms directly into Cloudflare's redirect syntax.
- [addRedirect API handler](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/astro/src/routes/api/publishing.ts#L117).

**What / why**

The CMS intends to refuse redirects that replace a real page, and its docs promise exact matches without wildcards. The validation does not implement that promise.

Local API tests reproduced an editor successfully committing both:

    { "from": "/listings/*", "to": "https://example.invalid", "status": 302 }
    { "from": "/listings/mill-house/", "to": "https://example.invalid", "status": 302 }

The fixture already serves /listings/mill-house. Its exact unslashed path is refused, but the trailing-slash variant passes and the output writer emits the unslashed rule too. Wildcards and named placeholders also pass, allowing a broad redirect to evade the exact page lookup.

Cloudflare explicitly supports wildcard and placeholder sources and applies asset redirects even when the requested asset exists. This can divert a whole collection or public site to an external destination after deployment. Source: [Cloudflare redirect syntax and precedence](https://developers.cloudflare.com/workers/static-assets/redirects/).

**Who / limitations**

A signed-in editor or owner can submit the rule. Editors are intentionally allowed to manage redirects; this finding concerns bypassing source restrictions, not missing owner-only permission. I did not publish a test redirect. Worker-served admin routes may be excluded by the deployment's routing configuration, so this is not a demonstrated interception of login callbacks.

**Suggested fix**

Reject wildcard and placeholder syntax if redirects are meant to be literal. Normalize source paths consistently before checking served pages, duplicates, and loops, including trailing slashes and relevant URL encoding. Apply the same rules to the API and build-time schema. Reserve admin, API, preview, and internal asset paths explicitly.

**Done when**

Tests refuse the two examples above, named placeholders, duplicate slash variants, and protected internal paths, while valid literal redirects continue to work.

### SEC-03 — Temporary uploads are not a private quarantine

**Where**

- [askUpload](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/astro/src/routes/api/media.ts#L209) mints an uploads/ key in the same R2 store.
- [presignUpload](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/core/src/media.ts#L258) signs only the PUT operation and key.
- [confirmUpload](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/core/src/media.ts#L329) validates later and writes the final object.
- [Documented public bucket setup](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/docs/media.md#L55).

**What / why**

The documented configuration attaches a public custom domain to the entire bucket. Temporary objects use an uploads/ prefix in that bucket; a prefix by itself does not make them private.

A local signature probe confirmed X-Amz-SignedHeaders is only **host**. An uploader can declare image/png to obtain a URL, then PUT different bytes with **Content-Type: text/html**, and omit confirmation. The later byte verification protects the final media key but does not protect public reads of the staging object. Under the documented setup, the uploader knows its public URL and can share active HTML or a phishing page on the media hostname.

The comment saying R2 cannot sign the type is inaccurate: Cloudflare documents signing Content-Type so a mismatch fails signature verification. Source: [R2 presigned URL restrictions](https://developers.cloudflare.com/r2/api/s3/presigned-urls/).

**Who / limitations**

Requires an authenticated uploader or someone holding a still-valid signed URL. The media hostname is separate from the CMS hostname, which limits direct same-origin access to the admin. Public exposure depends on there being no additional edge rule denying uploads/; dashboard rules were not inspected. No object was uploaded during this review.

**Suggested fix**

Use a genuinely private staging bucket and publish only verified bytes to the public bucket. Alternatively, serve objects through a gateway that allows only verified final keys and prevents access through every other public bucket hostname. Bind the permitted content type in the signature; force safe serving metadata and add nosniff on the public media response path. Keep the existing hash, size, byte checks, and verified-buffer finalization.

**Done when**

Anonymous requests for a staging key fail before and after upload; a mismatched PUT content type is refused; only successful validation produces a publicly readable object. Test all public bucket hostnames, not only the configured mediaBase.

### SEC-04 — Expensive CMS operations have no application-level abuse budget

**Where**

- [Upload URL issuance](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/astro/src/routes/api/media.ts#L209) has no per-user quota or outstanding-upload ledger.
- [Upload signing](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/core/src/media.ts#L259) does not bind the declared size; reconciliation rejects oversized objects only after storage.
- [Translation handler](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/astro/src/routes/api/entries.ts#L637) allows explicitly named fields to be translated repeatedly.
- [DeepL calls](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/core/src/translate.ts#L14) happen before draft-save conflict checks.
- [Draft body parsing](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/astro/src/routes/api/entries.ts#L456) buffers arbitrary JSON without a CMS size limit.

**What / why**

Better Auth's database-backed limiter protects authentication endpoints, not ordinary CMS uploads, translations, and saves.

An abusive or compromised editor can issue many upload URLs and send objects larger than the declared 10 MiB limit, consuming storage before confirmation or cleanup. Repeated named-field translation requests spend the site's provider quota even if later saves conflict. Very large draft JSON is parsed before rejection by downstream storage or validation.

This is a resource-consumption risk, not unauthenticated access. Provider/Cloudflare limits may cap the eventual damage, and external WAF rules may reduce it, but no per-user/site budget is enforced here. I did not perform load tests or incur provider charges.

**Suggested fix**

Introduce persistent per-user and per-site rate/concurrency limits for costly routes, a translation character budget with duplicate-request suppression, and an outstanding-upload/byte budget. A strict upload-byte ceiling requires enforcement before or during ingestion; checking the declaration and deleting later does not provide it. Add lifecycle expiry for abandoned staging objects independently of the application cron.

Use a bounded streaming body reader for JSON routes and cap nesting/collection sizes where useful. The [Canvas body reader](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/astro/src/routes/preview.ts#L148) already provides a pattern to reuse.

**Done when**

Excess work is rejected before external calls, duplicate translation requests share one operation, oversized JSON returns 413 before full buffering, and abandoned uploads expire even when the CMS cron is unavailable.

### SEC-05 — The admin shell can be framed by another origin

**Where**

[Admin HTML response](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/astro/src/routes/admin.ts#L105). In contrast, [preview responses](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/astro/src/routes/preview.ts#L28) already set frame-ancestors.

**What / why**

A local response test confirmed the admin shell sets neither a Content-Security-Policy frame-ancestors directive nor X-Frame-Options. Another site can put the admin in a disguised frame and try to steer a user into clicking real CMS controls.

SameSite=Lax reduces authenticated cross-site framing attacks, but does not stop a hostile **same-site sibling origin**, such as another subdomain. That distinction matters when the media and admin hosts share a registrable domain. This is deployment-dependent; an edge-supplied framing policy could already mitigate it.

**Suggested fix**

Set **Content-Security-Policy: frame-ancestors 'none'** on the admin shell if no legitimate embedding is needed, optionally with X-Frame-Options: DENY for older clients. Preserve preview's same-origin framing so Canvas still works. Apply the policy in the Worker response; do not assume a static-assets headers file covers dynamic admin HTML.

There is also no admin script CSP in this response. A compatible script policy would be useful additional hardening, but this review did not establish an admin XSS exploit.

**Done when**

The deployed admin refuses framing from an external origin and a same-site sibling origin, while the editor's preview still loads.

## Low-priority hardening

### SEC-06 — Private API responses lack a consistent no-store policy

**Where**

- [Middleware returns next() without applying response policy](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/astro/src/middleware.ts#L57).
- [Account response](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/astro/src/routes/api/members.ts#L26).
- [Member list response](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/astro/src/routes/api/members.ts#L99).
- [Entry response with draft content](https://github.com/MartinConde/handover/blob/768200e828e3d958e7f665c0f967e30a9e2a2672/packages/astro/src/routes/api/entries.ts#L164).

**What / why**

The shell, ping, and previews explicitly use private, no-store, but most authenticated JSON responses do not. These contain draft content, member addresses, and account/session metadata.

There is no demonstrated shared-cache disclosure here. This is a hardening gap: the application leaves retention and reuse to browser/cache defaults and deployment rules, making future caching changes riskier.

**Suggested fix**

Apply **Cache-Control: private, no-store** consistently to private CMS API responses and authentication responses, including errors. Check Worker/CDN cache rules exclude those routes. Keep versioned public JavaScript and CSS cacheable.

**Done when**

Header tests cover account, members, entries, history, settings, and unauthorized responses, and the deployed responses retain the policy.

## Validation and boundaries

- **697 existing tests passed** across 11 selected files covering core authentication, rich text, redirects/lifecycle, media, settings encryption, Astro middleware/auth, API handlers, preview, base paths, and admin responses. This was not the entire repository test suite.
- **Five additional local probes passed**, confirming current behavior: redirect validation/output bypass, two API redirect bypasses, an unrestricted upload signature, and missing admin framing headers. Temporary probe files were removed after the review.
- Registry audit counts: CMS full tree **1 critical / 6 high / 9 moderate**; demo **1 / 8 / 4**; scratch **1 / 4 / 2**. CMS production-only was **0 / 0 / 3**. These counts overlap across packages/projects and are not counts of independently exploitable CMS vulnerabilities.
- Reviewed safeguards include closed signup, explicit authentication endpoint allowlisting, server-side owner checks for member/settings administration, hashed magic links, session cookie controls, parameterized database operations, encrypted integration keys, preview authentication/origin/body checks, constrained rich-text rendering, and verified upload finalization.
- Astro's current origin-check implementation and documentation were inspected, so the absence of a second CSRF check in CMS middleware was not reported as a standalone vulnerability. The installed framework also normalizes request paths before exposing them to middleware.
- No production exploit was attempted. External R2 access policies, CDN response headers, deployment artifacts, and identity-provider configuration remain runtime verification points.

Only this report and the advisory inventory were retained; no application fixes, dependency upgrades, or deployment changes were made.
