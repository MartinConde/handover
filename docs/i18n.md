# Languages

Every site declares its languages, a site with one language included. Content files live
in a folder per language either way, so adding a second one later is a config change and a
copy rather than a move of every file.

```ts
// cms.config.ts
export default defineConfig({
  i18n: { locales: ['en', 'de'], defaultLocale: 'en' },
  collections: { /* … */ },
});
```

| Key | Required | What it is |
|---|---|---|
| `locales` | yes | The folder names under `src/content/<collection>/`, in the order the admin shows them. Lowercase letters, digits and dashes: `'en'`, `'de'`, `'pt-br'` — never `'en_US'`. |
| `defaultLocale` | yes | One of `locales`. The language a translation is made from, and the one whose URLs have no language segment. |
| `prefixDefaultLocale` | no | `false` by default: `/about` in the default language and `/de/about` in the others. `true` puts every language under its own segment. |

## It has to match `astro.config.mjs`

Astro builds the pages from its own `i18n` block and Handover writes the files and the
preview paths from this one, so the two have to say the same thing. Declare it in both:

```js
// astro.config.mjs
export default defineConfig({
  adapter: cloudflare(),
  i18n: { locales: ['en', 'de'], defaultLocale: 'en' },
  integrations: [handover(cms)],
});
```

Where they disagree the build stops before anything is served, naming both files:

```
cms.config.ts › i18n.defaultLocale: "de" is not astro.config.mjs's i18n.defaultLocale "en"; the two must match exactly
```

`prefixDefaultLocale` is Astro's `i18n.routing.prefixDefaultLocale`; leaving it out on both
sides is a match. A locale Astro spells as `{ path: 'de', codes: ['de', 'de-AT'] }` matches
`'de'` here — the path is the folder name and the URL segment, which is what a locale is here.

## The files

One folder per language inside the collection, and the same file name in each:

```
src/content/
  pages/
    en/home.yaml
    de/home.yaml
  listings/
    en/seaview-cottage.yaml
    de/seaview-cottage.yaml
```

The globals ([Site files](site-files.md)) sit the same way.

The **file name is the entry**, across every language: `pages/en/home.yaml` and
`pages/de/home.yaml` are one entry in two languages, linked by their name and nothing else.
Renaming it renames it in all of them. `de/impressum.yaml` with no English counterpart is an
entry that exists in German alone, and needs no flag.

One folder deep and no deeper: a file anywhere else under `src/content/` fails the build
naming itself ([Drafts and publishing](publishing.md#the-content-index)).

## Which fields are translated

Every field is translated by default. One that should read the same in every language, or
belong to the default language alone, says so in the schema.

```ts
// src/content/schemas.ts
export const listing = z.object({
  title: z.string(),                                   // a value per language
  price: z.number().meta({ i18n: 'duplicate' }),       // the same value in every language
  notes: z.string().optional().meta({ i18n: false }),  // the default language only
});
```

| `i18n` | What it means |
|---|---|
| `true`, or nothing at all | Translated. Each language has its own value. |
| `'duplicate'` | Shared. The value is written to every language's file, so a change to it changes all of them. |
| `false` | The default language only. The other languages neither show it nor carry it. |

An object hands its mode to the fields inside it, and a field inside can say otherwise:

```ts
const contact = z
  .object({ name: z.string(), role: z.string().meta({ i18n: true }) })
  .meta({ i18n: 'duplicate' }); // name is shared, role is translated
```

### An image is both at once

`image`, `file`, `embed`, `link` and `seo` are one field with a translated part and a shared
part, because that is how they are used: the same photo, described in each language.

| Field | Translated | Shared |
|---|---|---|
| `image` | `alt` | `src`, `width`, `height`, `focal` |
| `file` | `name` | `src`, `bytes`, `mime` |
| `embed` | `title` | `provider`, `id`, `start` |
| `link` | `label` | `type`, `href`, `ref`, `newTab` |
| `seo` | `title`, `description`, `image.alt` | the rest of `image`, `noindex`, `canonical` |

`.meta({ i18n: 'duplicate' })` on one of them overrides the split and shares the whole value.

## The structure is shared

Which blocks an entry has, and in which order, is the same in every language — only the values
differ. So adding a block, removing one or dragging one somewhere else is an edit to **every**
language's file, and the admin writes them all in one go:

```
src/content/pages/en/home.yaml   hero, cta          →   cta, hero
src/content/pages/de/home.yaml   hero, cta          →   cta, hero
```

The German file keeps its German. A block that moves takes its translation with it, a block
that arrives brings the shared values it already has — an image's `src`, a price — and nothing
to read yet. A save that changed neither the structure nor a shared value does not touch the
other files at all, and a language the entry has no file in is left without one: nothing is
created behind your back.

### A block one language only has

Give it `_locales` and it is written to those files and to no others
([Content format](content-format.md#reserved-keys)):

```yaml
blocks:
  - _type: "compliance"
    _id: "p8xk2m4q"
    _locales:
      - "de"
    heading: "Widerrufsbelehrung"
```

`de/home.yaml` has it, `en/home.yaml` does not, and neither file is wrong. It holds its place:
a block put after the hero in German stays after the hero when English reorders around it.

A block that appears in one language *without* `_locales` is a different thing — two files that
have drifted apart, usually a hand edit or a bad merge. A save never resolves that by itself:
it leaves such a block exactly where it is rather than copying it into the other language or
dropping it. Reconciling the two is a decision somebody makes, in the admin
([Translating](translating.md#when-the-languages-disagree)).
